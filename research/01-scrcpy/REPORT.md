# Эксперимент 01 — запись звонка с правами shell (scrcpy 5.0.1)

Дата: 23.11.2026, 12:00–12:03. Устройство: Xiaomi 14T Pro (2407FPN8EG), HyperOS OS3.0.304.0.WNNMIXM, Android 16 / SDK 36, MediaTek Dimensity 9300+. Звонилка — Google Phone 248. Одна SIM.

## Цель
Проверить, отдаёт ли аудиостек этого телефона обе стороны разговора процессу с правами shell (uid 2000, тот же уровень, что даёт Shizuku), без root и без громкой связи.

## Предпосылка (adb)
`dumpsys package com.android.shell`: shell имеет `CAPTURE_AUDIO_OUTPUT`, `CAPTURE_VOICE_COMMUNICATION_OUTPUT`, `CALL_AUDIO_INTERCEPTION`, `MODIFY_PHONE_STATE` (granted=true). Обычному приложению эти разрешения недоступны (signature|privileged), роль DIALER их не даёт. Системный `com.mediatek.callrecorder` (priv-app) требует `PROCESS_CALL_RECORD` (signature|privileged) — для сторонних приложений закрыт.

## Методика
- scrcpy `--no-video --no-playback --no-control --audio-codec=raw --time-limit=40`, источники по очереди в одном звонке: `voice-call`, `voice-call-uplink`, `voice-call-downlink`.
- Перед каждой записью снимок состояния (`*.state.txt`): `mCallState=2`, `MODE_IN_CALL`, активное устройство — **earpiece** (громкая связь выключена), экран включён.
- Разговор — попеременная диктовка размеров.
- Анализ: уровни по окнам 0,5 с, доли энергии по полосам, корреляция каналов, участки цифрового нуля (`analysis.json`).

## Результаты

| Источник | Файл | Формат | Уровень / пик | Речь в окнах | Каналы |
|---|---|---|---|---|---|
| voice-call | voice-call.wav | 48 кГц, стерео, 40,1 с | L −20,6 / −0,9 dBFS; R −23,1 / 0 dBFS | L 89 %, R 78 % | **независимые, корреляция 0,002** |
| voice-call-uplink | voice-call-uplink.wav | 48 кГц, моно×2, 40,2 с | −25,6 / 0 dBFS | 70 % | L=R |
| voice-call-downlink | voice-call-downlink.wav | 48 кГц, моно×2, 40,2 с | −24,6 / −1,2 dBFS | 84 % | L=R |

- `voice-call` отдаёт **две независимые дорожки** — по стороне на канал. Доля тишины в R (55 %) совпадает с uplink (54,5 %) → предположительно **L = собеседник, R = вы** (подтвердить прослушиванием `voice-call_L.wav` / `voice-call_R.wav`).
- Цифровой ноль появляется участками 0,2–4,9 с и совпадает с паузами говорящего (подавление тишины в канале связи), провалов внутри речи по разметке не видно.
- Полоса: 78–90 % энергии в 300–3400 Гц, выше 3,4 кГц < 1,5 % → звонок шёл в узкополосном («обычном телефонном») качестве; при HD-голосе (VoLTE/AMR-WB) полоса будет шире. Это свойство сети/звонка, не записи.
- Ошибок захвата нет (stderr: только служебные строки scrcpy).

Производные файлы: `voice-call_mono_mix.wav` (L+R — то, что будет сохранять приложение), `voice-call_L.wav`, `voice-call_R.wav`.

## Вывод
На Xiaomi 14T Pro / Android 16 процесс с правами shell записывает **обе стороны разговора без громкой связи** через `AudioSource.VOICE_CALL`. Окончательный критерий (разборчивость обоих голосов) — прослушивание.

## Не проверено в этом эксперименте
- Заблокированный экран (экран был включён).
- Автоматический старт/стоп по событиям звонка (запись запускалась вручную по `mCallState`).
- Входящий и исходящий по отдельности (тип этого звонка не фиксировался).
- Старт после перезагрузки.

## Автозапуск Shizuku после перезагрузки (исследование исходников)
Shizuku v13.6.0 (25.05.2025): «Support auto start without root on Android13+ when connected to a trusted WiFi». `BootCompleteReceiver.adbStart()`: при `BOOT_COMPLETED` включает беспроводную отладку и подключается к локальному adbd своим ключом. Условия: Android 13+; Shizuku выдано `WRITE_SECURE_SETTINGS` (`pm grant` один раз с компьютера); последний запуск был через ADB; **в момент загрузки есть Wi-Fi**, ожидание порта всего 3 с. Повторной попытки при появлении Wi-Fi позже нет. На HyperOS дополнительно нужен «Автозапуск» для Shizuku. Проверить на устройстве.
